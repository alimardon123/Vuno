Reviewed 23 Aug 2026 against `5e48d50` on `claude/teams-communication-app-9ttkqp`.
Method: installed the app, ran it against the committed database, drove it in a real

## Summary

There are two products here. The communication app is thin. The evidence system —
the only reason to build this rather than use Buzz — is a recording of a debate that
never happened. Both are fixable. The schema and the ADRs are good and should survive.

## Findings

### C1 — Debate does not transition claims. It writes conclusions. *(critical)*

`src/app/api/debate/route.ts:123,359,415`

The product's differentiating idea is that debate is the state-transition function:
a claim moves `asserted → believed → falsified` because evidence arrived. The code
does not do this. Each run mints a decision id from the clock, derives a claim id
from it, and inserts a new row **born** `falsified`. No claim is ever read or updated.

```
const decisionId = `dec-${Date.now().toString(36)}`;   // line 123
const claimId    = `claim-${decisionId}`;              // line 359
await db.claim.create({ status: 'falsified', ... })    // line 415
```

Visible in the shipped database — nine runs, nine identical claims:

```
sqlite> SELECT statement, status, COUNT(*) FROM Claim GROUP BY 1,2;
p99 read latency < 50ms at 10k concurrent readers | falsified | 9
Bloom filters add ~1.5x memory overhead...        | tested    | 1
```

**Fix.** Stable claim identity, a status history, and a `ClaimStatusChanged` event the
projection folds. The debate route reads the claim and appends; it never inserts a
conclusion. Everything the product promises is downstream of this.

### C2 — The whole app is one route with no URLs *(critical)*

`src/app/page.tsx` renders `<AppShell/>` and that is the entire routing surface. Active
channel, open decision and current view live in a Zustand store, not the address bar.
No deep links, no browser back, no shareable decision, no restored session, no SSR.

**Fix.** `/c/[channel]`, `/c/[channel]/t/[thread]`, `/d/[decision]`, `/ledger`.

### H1 — 40 type errors, invisible because the build ignores them *(high)*

`next.config.ts` sets `typescript.ignoreBuildErrors: true`. Behind it: `chat-view.tsx`
reads `channel.isDm` off a type that does not declare it (4×); `message-bubble.tsx`
reads `scopeType`/`scopeId` off a projection that has neither; `debate/route.ts` writes
a `rejectedAlternatives` shape the event union rejects. Each is a field that is
`undefined` at runtime and silently takes a branch.

**Fix.** Turn the flag off, drive the count to zero, add CI.

### H2 — The Channels panel lists direct messages as channels *(high)*

`src/components/left-rail/channels-panel.tsx:50` renders everything `/api/channels`
returns without filtering `isDm`, so the list shows `# Aris`, `# Bob`, `# Kai`, `# Sid`.
The worklog records this fixed in "Round 30"; the fix landed in the Chats panel only.
Same round left *Create channel* as a button with a `TODO` and an empty handler.

**Root cause.** `Channel` carries `isDm` plus a nullable `teamId`, and four components
each re-derive "channel vs DM vs group chat" with different logic. One discriminated
`kind` field, resolved server-side, in one place.

### H3 — The design system is a description of a competitor *(high)*

`docs/design/DESIGN_SYSTEM.md` opens "inspired by Buzz from Block… warm cream
backgrounds, mustard/gold accents"; `globals.css` cites "VLM analysis of the Buzz
screenshot" and lists Buzz's hex values. Buzz shipped July 2026 and is the closest
competitor this product has. It is also the single most over-used look in
AI-generated interfaces.

**Fix.** Graphite chrome; saturated colour reserved for claim status and gate state.
See the artifact for the direction rendered live.

### M1 — Identity is inconsistent and the seed contradicts itself *(medium)*

Bob is Kai's personal assistant in the sidebar and "Product Lead" in the member list of
the same screen. A DM with Aris shows a nine-member roster. The org panel counts 10
members and lists 8. There is a channel `dm-user-kai-user-kai` — Kai in a DM with
himself. Every department has exactly one team.

**Fix.** One server-side roster resolver per scope; a seed that reads like a company.

### M2 — "Installation should be simple" is not currently true *(medium)*

Committed `.env` reads `DATABASE_URL=file:/home/z/my-project/db/custom.db` — an absolute
path from the generating machine. `bun.lock` pinned 937 tarballs to
`registry.npmjs.com` rather than canonical `registry.npmjs.org` (fixed in this commit).
Startup hard-codes port 3000 and shells out to a Caddyfile. A first-time clone does not run.

**Fix.** Relative SQLite path, `.env.example` committed and `.env` ignored, one
`bun run setup` that installs, migrates, seeds and starts.

### Keep — what is genuinely good

- **The schema.** Append-only event spine with monotonic `seq`, polymorphic scope, and a
  deliberate comment explaining why `scopeId` is not a FK. Claims carry provenance and
  evidence. The work graph is modelled correctly. This is the expensive part and it is right.
- **Six numbered ADRs**, each pinned to a decision.
- **The three-tier attention router** — deterministic rules, cheap classifier, full wake.
  Correct economics, already sketched in `src/lib/agents/attention-router.ts`.
- **The adapter seam** — `role → model → harness` separated, simulated adapter beside a real one.
- **The worklog** — 266 KB of research/action/result/adjustment cycles.

## Competitive read

| Product | Shipped | The bet | Take | Room it leaves |
|---|---|---|---|---|
| **Buzz** (Block, Apache 2.0) | Jul 2026 | Human–agent parity as cryptography — signed Nostr events, agents hold scoped keypairs tied to an owner, revocable individually | Agent identity as a credential, not `kind: 'agent'`. Chat merged with the forge: a git branch *is* a thread | Parity governs who may speak and sign. It says nothing about whether what was said was right. No claims, no status, no evidence |
| **Paperclip** (MIT) | Mar 2026 | Org chart as runtime — roles, budgets, approvals, heartbeat wakes, goal ancestry. Aimed at "zero-human companies" | Budgets as core primitives. Heartbeat wake as default. ~70k stars says the org metaphor lands | An orchestrator, not a place. No ambient conversation. Its goal — removing the human — is the opposite of yours |
| **Multica** (OSS) | 2026 | Agents as teammates you assign issues to; 23 agent CLIs; bridges into Slack/Lark/Telegram | Harness plurality shipped. Humility of bridging rather than replacing | A dashboard bolted onto someone else's chat; conversation and work record drift apart |
| **Mattermost / Zulip** | mature | Self-hosted chat that actually works | Zulip's topic model is the best threading design in the category | No agent model — but they set the floor on pure chat quality, and it is high |

**The gap.** Buzz proves *who* said it. Paperclip proves *who authorised* it. Multica
proves *what got done*. None keeps a record of what the organisation currently believes,
how confident it is, and what would change its mind. That is the ledger — an unoccupied
position, which is why C1 is the most serious finding here.

**The other gap.** None of the three is *nice to be in*. "At least a sleek, user-friendly,
beautiful communication app" is not a consolation prize; it is a differentiator none of
them is contesting.

## The risk you named, priced

Riskiest assumption #1 in the vision doc — "that debate improves output enough to justify
its cost" — was the right call, and the 2025–26 literature has moved against it:

- Most multi-agent-debate frameworks do not beat plain chain-of-thought at matched budget.
- Debate typically costs 3–10× a single well-designed agent.
- Homogeneous debate shows stance homogenisation and factual attrition.
- Isolated self-correction often beats unguided debate outright.
- Multi-agent wins in a narrow band: parallelisable, read-heavy work over independent sub-questions.

What survives is the good part: those are failures of *unguided, homogeneous* debate.
The design already avoids both — evidence outranks assertion, experiments break ties,
roles are assigned across model families. Heterogeneous debate with evidence weighting is
the configuration that still shows gains. But the value is in **measurement settling
arguments** and **the record of what was measured**. Position on the ledger, not the debate,
and keep the debate engine as small as it can be while still producing claim transitions.

**Week-one experiment.** One real architecture decision, three ways at matched token
budget: single strong model; same model self-critiquing; structured debate across three
families. Score blind. Record all three as claims in the ledger. If debate loses, the
product has falsified its own premise — the most convincing demo it could give, for ~$40.

## Build plan

Each phase has an exit gate. If the gate does not pass, the phase is not done.

**P0 — Make it run for a stranger (~1 day).** Portable `.env`, `.env.example`, one setup
script, `ignoreBuildErrors` off and 40 → 0, CI on typecheck and lint.
*Gate: fresh clone → one command → working app on a machine that has never seen the repo.*

**P1 — Falsify the premise before building on it (~3 days).** The matched-budget experiment
above. Deliberately before the redesign: if debate loses badly, the product is "a beautiful
agent-native chat app with an audit ledger" — still good, different roadmap.
*Gate: a written result with numbers and cost, either way.*

**P2 — Fix the ledger so it is a state machine (~1 week).** Stable claim identity;
`ClaimStatusChanged` carrying prior status, new status, triggering evidence, reason; debate
reads and appends. Ledger renders the transition trail.
*Gate: one claim, four status changes, one row, full trail. Replaying the log from seq 0
reproduces current state exactly. Duplicate claims impossible.*

**P3 — Rebuild the shell on real routes (~2 weeks).** Routes and deep links; one
discriminated conversation model resolved server-side; dense virtualised message list;
typed composer as the primary composer; keyboard navigation; both themes designed.
*Gate: every surface has a pasteable URL. 60 fps at 5,000 messages. Full keyboard
operation. No developer copy visible to users.*

**P4 — One honest agent in one channel (~1 week).** Not six simulated ones. One real agent
on a real harness, attention router actually gating wakes, visible budget, able to attach
evidence and move a claim.
*Gate: tier-1 deterministic rules cause ≥70% of useful wakes. Cost per resolved decision recorded.*

**P5 — Then the org layer.** Teams, gates as ledger queries, HR metrics, promotion.
Straightforward after P2, impossible before — as the vision doc already says.
*Gate: a gate that blocks a release from a ledger query, with a human able to read why in one screen.*

## Carried forward from P3

**The typed composer needs a decision to attach to.** The composer offered Message /
Objection / Evidence / Proposal tabs. Selecting one changed the placeholder text and
nothing else — every send posted a plain `MessagePosted`, because `ObjectionRaised`,
`EvidenceAttached` and `ProposalOpened` all carry a `decisionId` (`src/lib/events/types.ts`)
and a conversation has no decision to attach them to. The tabs are removed rather than
left lying. Restoring them needs one of:

- a channel that knows its project, so a composer can open a decision in scope; or
- opening a decision from the conversation, and the typed tabs appearing inside it.

The second is closer to the vision doc's "the record and the conversation are the same
place", because the decision is the record. It belongs with the Work surface, not with the
shell.

**`prisma db push` is not a migration story.** `bun run setup` pushes the schema, which
silently drops columns on change — acceptable for a local dev database, not for an
instance holding a real org's event spine. Before anyone runs this on data they care
about, `setup` needs `prisma migrate deploy` against a committed migration history.

## The simulated agents are gone

ADR-0002 called them "v1 — being replaced". What they actually were: a keyword
table. Posting *"I am worried about the security of the new read path"* in a
channel produced five events — a "security glance" from Sid, a "counterpoint"
from Devi, two facts Bob had "learned" about you, a proactive note, and a
handoff after which Sid posted again with the line *"Security-wise on
security: threat model first"*, a template collision that gave the whole thing
away. Substring matching on "security", hand-written replies, attributed to
members of the org.

That is the scripted theatre CLAUDE.md rules out, and it fired on every message
a person posted. Removed:

| | |
|---|---|
| `/api/attention-router` | matched substrings, woke up to two agents, posted their canned observations |
| `/api/memory-evolution`, `/api/personal-memory`, `/api/agent-memory` | the assistant "learning" — substring matching, no ML, by its own comment |
| `lib/agents/{attention-router,memory-detector,proactive-note-generator,handoff-router}.ts` | the keyword tables and templates behind all of it |
| `lib/agents/adapters/simulated.ts` | 899 lines of canned responses per trigger type |
| `lib/agents/adapters/llm.ts`, `lib/agents/llm-brief.ts` | bound to an SDK needing a `.z-ai-config` that no install has |
| `/api/thoughts`, `/api/trace`, `/api/wiki`, `/api/hr-metrics` | surfaces of the old shell, unreachable since P3 |
| `/api/agents`, `/api/users` | shims their own comments said to remove "when the shell rebuild lands" |

`/api/events` was rewritten rather than removed. It proxied appends to a Rust
service on port 3030 and fell back to Prisma when it was down — nothing starts
that service, and if anything did there would be two processes assigning `seq`
to the same log, which ADR-0008 exists to prevent. It also accepted
`AttentionWakeup`, `MemoryUpdated`, `PaProactiveNote` and `AgentHandoff` from
an unauthenticated POST and wrote every event with no actor at all.

`/api/install` no longer defaults an agent to `simulated/echo-1` on the
`simulated` harness. Naming what will run an agent is part of hiring it.

**What the organisation still does on its own**, with no model configured:
routes an objective to a department, assembles a working group, interrogates
the requirements, evaluates gates as queries over the ledger, and transitions
claims. All deterministic, all real.

**What it cannot do yet**: anything that needs a model. There is no adapter
registry and the orchestrator has never invoked an adapter — ADR-0006 is a
contract with no implementations behind it. That is P4, and it is now the
honest next step rather than something the keyword table was pretending to
cover.

**Four event types nothing emits.** `AttentionWakeup`, `MemoryUpdated`,
`PaProactiveNote` and `AgentHandoff` remain in the vocabulary and the chat
projection renders them, so an existing database still displays its history.
Nothing writes them.

## P4: one honest agent

ADR-0006 described an adapter interface and a registry. The interface existed;
the registry did not, and the orchestrator had never invoked an adapter in its
life. What filled the gap was the keyword table above.

What is there now:

- **`lib/agents/registry.ts`** resolves what will run an agent from its own
  `harnessName`, and when nothing can, says which environment variable would
  fix it. Two harnesses: `anthropic` (a key) and `ollama` (a local model, no
  key, no account, no per-token cost).
- **`lib/agents/prompt.ts`** — one prompt for both harnesses, so moving an
  agent between them changes what runs it and not who it is. Two rules do the
  work: say what would falsify a claim, and say you do not know rather than
  filling the gap. A ledger of confident guesses is worse than an empty one,
  because the gates read from it.
- **`lib/agents/turn.ts`** — work item → adapter → validated events on the
  spine. Nothing a model produces reaches the spine unchecked; it goes through
  `parseAgentOutput`, and what that refuses is reported rather than dropped. A
  claim an agent proposes is asserted even when the model says "tested":
  a measurement moves a claim there, and the agent is not the one recording it.
- **`@mention` → `agent_turn`** — a lookup against handles that exist. The
  conversation is unchanged by it: a DM summoning an assistant is still a DM,
  same members, same name, same place in the sidebar. Only your own assistant
  carries your authority; calling on Sid gets Sid's opinion, not something said
  in your name.
- **Every run records what it cost** — tokens in and out, cents, model,
  harness — including the runs that cost nothing, because "every run records
  its cost" is only checkable if the zero ones are recorded too.

**With no model configured**, mentioning an agent queues a turn that fails on
the first attempt with the reason. It is not retried: no number of attempts
produces an API key. Activity says it once at the top, and the failure appears
under "Work that failed" naming the variable to set.

Tested without a model: 39 tests over the registry, both adapters against a
stub, mention extraction, and the whole path end to end — including the live
one, driven against a stub server over real HTTP through `ANTHROPIC_BASE_URL`,
so an install that adds a real key gets behaviour that has been exercised.

## The Library, and what is deliberately not in it

`Skill` and `MemberSkill` hold instructions an agent can be given, written as
SKILL.md bodies rather than in a format invented here. The thing that makes it
real rather than a table: `src/lib/agents/turn.ts` loads what a member holds on
every turn and `systemPrompt` puts it in the instructions verbatim. Giving Peri
the benchmark methodology changes what Peri does the next time it is asked
something, which is why the IA calls assignment a staffing decision rather than
a setting. A test drives a turn against a stub server and asserts the skill's
text arrives in the system prompt.

**MCP connections are not here yet, on purpose.** They belong in the same
library — the IA is explicit that skills, connections and runtimes are one
section, because all three answer "what is this agent made of". But a row
declaring a connection nothing can call would describe a capability the org does
not have, which is the same failure as the simulated agents. Adding it means
building the call path first: an MCP client, per-agent scopes, and a record of
what each tool call did and cost, on the same `WorkSession` the model calls use.

**The agent package manifest is still 60% done.** `POST /api/members` takes
name, kind, role, model, harness, team and owner. The IA lists what is missing:
`prompts`, `requiresSkills`, `requiresMcp`, `mayBlockGates`, `permissions`
(present on the schema, still unread), `evaluation`, and version/author
provenance. `requiresSkills` is the one with somewhere to point now.

## What stands between this and production

**Authentication now exists.** It did not: whoever reached the port was the org
owner, and `next-auth` was installed and wired to nothing. There is a `Session`
table, scrypt password hashes, a sign-in page, middleware that turns away every
route but `/sign-in` and `/api/auth`, and `currentViewer()` / `viewerFromRequest()`
in place of `getOrgOwner()` in all twelve places it stood in for "who is
viewing". A DM finally names itself from whoever is reading it, which was
untestable while there was only one possible reader.

Two things worth recording about how it went wrong first:

- The first version hashed with `Bun.password`. Every unit test passed and the
  app returned 500 on sign-in, because Next runs route handlers in a
  Node-compatible runtime where `Bun` is undefined — and `bun:test` *is* Bun.
  It uses `scrypt` from Node's own crypto now, and the smoke test signs in, so
  a runtime-only failure cannot pass again.
- The sign-in button fired both its own `onClick` and the form's `onSubmit`, so
  it posted twice; the second claim failed with "already claimed" and clobbered
  the first one's redirect. Guarded with a ref, because React state is not
  updated synchronously and a `busy` flag cannot see its own change.

**Conversation access is enforced now.** Being signed in was not the same as
being in a conversation: any member could open, post into, or subscribe to
anyone's DM by knowing its id. `canRead` decides it in one place, and the list,
the page, the write routes and the SSE stream all go through it. An assistant
reads whatever its owner reads (ADR-0009 §2) — asked for explicitly, and what
makes an assistant useful rather than a chatbot with amnesia.

Reading unfiltered now takes the word `'system'`, because the one way this
check gets skipped is a forgotten argument, and two page callers had already
forgotten it.

**Rate limiting** counts writes per member, in memory, per process — 60 a
minute. Deliberately not durable: a counter on the write path of every message
is another table, and this exists to stop a runaway script and a stuck retry
loop, not an adversary with a botnet. By member and not by IP, because limiting
by IP punishes an office behind one router and does nothing to a script running
locally, which is the case this actually guards.

**Getting the org out** — `bun run export` (JSON, events first) and
`bun run export --backup` (a checkpointed copy of the file). Verified by opening
a backup with a fresh client: the org, its events, its claims, and a gapless
spine.

**Still missing:** `Event.visibility` itself is written and unread — the
column allows `team` and `private` scopes that nothing narrows to. Conversation
membership covers the case that mattered; per-event visibility inside a
conversation does not exist yet.

**Other gaps, in the order they would bite:**

| | |
|---|---|
| SSE polls per open conversation | fine at this scale, wrong shape at a hundred concurrent readers |
| `Event.visibility` written, never read | every event inside a conversation is visible to everyone in it |
| Rate-limit counters live in one process | correct for one server; a second one needs somewhere shared to put them |
| Most of the agent package manifest | prompts, required skills and connections, gates it may block, permissions, evaluation, version — designed in ADR-0006, not built |

Four of the original entries are fixed rather than listed: rate limiting, export
and backup, and the two below. Mentions are capped at
three agents per message — every mention is a model call somebody pays for, and
a pasted list of handles should not be able to empty a budget. And there is a
daily spend ceiling (`VUNO_DAILY_BUDGET_CENTS`, default $5.00): checked before
the model call rather than after, because a budget enforced on the way out has
already spent the money it was meant to stop. Past it, agent turns fail saying
how to raise it, and Review shows today against the ceiling.

None of the rest are hard individually. They are listed because "production ready"
is a claim somebody will make about this, and it should be made against a list
rather than a feeling.

## Open questions

1. **Rebuild the shell, or renovate it?** — *Recommend:* keep `prisma/`, `src/lib/`, `docs/`;
   rebuild `src/app/` and `src/components/` on real routes.
2. **Who is the first user — you alone, or a team?** — *Recommend:* solo-first. One human,
   one assistant, one channel, ledger visible from day one.
3. **How different from Buzz do you want to look?** — *Recommend:* the graphite direction
   in the artifact. I would not ship the current palette.
4. **Local-first, or server-first with local as a mode?** — *Recommend:* single-process local
   now, every write through the event spine with a monotonic sequence, which keeps sync possible later.
5. **Desktop app, or browser?** — *Recommend:* build desktop-ready, wrap in Tauri at P3.
6. **What demo do you want to be able to give in six weeks?** — *Recommend:* the falsification
   demo with a real benchmark against a real storage engine.
7. **Which harnesses and models do I have?** — Model plurality is load-bearing; adversarial
   review needs the reviewer on a different family from the proposer.
