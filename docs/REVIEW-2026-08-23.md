## Findings

### C1 — Debate does not transition claims. It writes conclusions. *(critical)*

`src/app/api/debate/route.ts:123,359,415`

The product's differentiating idea is that debate is the state-transition function:
a claim moves `asserted → believed → falsified` because evidence arrived. The code
does not do this. Each run mints a decision id from the clock, derives a claim id
from it, and inserts a new row **born** `falsified`. No claim is ever read or updated.

```
const decisionId = `dec-${Date.now().toString(36)}`;   // line 123
const claimId    = `claim-${decisionId}`;              // line 359
await db.claim.create({ status: 'falsified', ... })    // line 415
```

Visible in the shipped database — nine runs, nine identical claims:

```
sqlite> SELECT statement, status, COUNT(*) FROM Claim GROUP BY 1,2;
p99 read latency < 50ms at 10k concurrent readers | falsified | 9
Bloom filters add ~1.5x memory overhead...        | tested    | 1
```

**Fix.** Stable claim identity, a status history, and a `ClaimStatusChanged` event the
projection folds. The debate route reads the claim and appends; it never inserts a
conclusion. Everything the product promises is downstream of this.

### C2 — The whole app is one route with no URLs *(critical)*

`src/app/page.tsx` renders `<AppShell/>` and that is the entire routing surface. Active
channel, open decision and current view live in a Zustand store, not the address bar.
No deep links, no browser back, no shareable decision, no restored session, no SSR.

**Fix.** `/c/[channel]`, `/c/[channel]/t/[thread]`, `/d/[decision]`, `/ledger`.

### H1 — 40 type errors, invisible because the build ignores them *(high)*

`next.config.ts` sets `typescript.ignoreBuildErrors: true`. Behind it: `chat-view.tsx`
reads `channel.isDm` off a type that does not declare it (4×); `message-bubble.tsx`
reads `scopeType`/`scopeId` off a projection that has neither; `debate/route.ts` writes
a `rejectedAlternatives` shape the event union rejects. Each is a field that is
`undefined` at runtime and silently takes a branch.

**Fix.** Turn the flag off, drive the count to zero, add CI.

### H2 — The Channels panel lists direct messages as channels *(high)*

`src/components/left-rail/channels-panel.tsx:50` renders everything `/api/channels`
returns without filtering `isDm`, so the list shows `# Aris`, `# Bob`, `# Kai`, `# Sid`.
The worklog records this fixed in "Round 30"; the fix landed in the Chats panel only.
Same round left *Create channel* as a button with a `TODO` and an empty handler.

**Root cause.** `Channel` carries `isDm` plus a nullable `teamId`, and four components
each re-derive "channel vs DM vs group chat" with different logic. One discriminated
`kind` field, resolved server-side, in one place.

### H3 — The design system is a description of a competitor *(high)*

`docs/design/DESIGN_SYSTEM.md` opens "inspired by Buzz from Block… warm cream
backgrounds, mustard/gold accents"; `globals.css` cites "VLM analysis of the Buzz
screenshot" and lists Buzz's hex values. Buzz shipped July 2026 and is the closest
competitor this product has. It is also the single most over-used look in
AI-generated interfaces.

**Fix.** Graphite chrome; saturated colour reserved for claim status and gate state.
See the artifact for the direction rendered live.

### M1 — Identity is inconsistent and the seed contradicts itself *(medium)*

Bob is Kai's personal assistant in the sidebar and "Product Lead" in the member list of
the same screen. A DM with Aris shows a nine-member roster. The org panel counts 10
members and lists 8. There is a channel `dm-user-kai-user-kai` — Kai in a DM with
himself. Every department has exactly one team.

**Fix.** One server-side roster resolver per scope; a seed that reads like a company.

### M2 — "Installation should be simple" is not currently true *(medium)*

Committed `.env` reads `DATABASE_URL=file:/home/z/my-project/db/custom.db` — an absolute
path from the generating machine. `bun.lock` pinned 937 tarballs to
`registry.npmjs.com` rather than canonical `registry.npmjs.org` (fixed in this commit).
Startup hard-codes port 3000 and shells out to a Caddyfile. A first-time clone does not run.

**Fix.** Relative SQLite path, `.env.example` committed and `.env` ignored, one
`bun run setup` that installs, migrates, seeds and starts.

### Keep — what is genuinely good

- **The schema.** Append-only event spine with monotonic `seq`, polymorphic scope, and a
  deliberate comment explaining why `scopeId` is not a FK. Claims carry provenance and
  evidence. The work graph is modelled correctly. This is the expensive part and it is right.
- **Six numbered ADRs**, each pinned to a decision.
- **The three-tier attention router** — deterministic rules, cheap classifier, full wake.
  Correct economics, already sketched in `src/lib/agents/attention-router.ts`.
- **The adapter seam** — `role → model → harness` separated, simulated adapter beside a real one.
- **The worklog** — 266 KB of research/action/result/adjustment cycles.

## Competitive read

| Product | Shipped | The bet | Take | Room it leaves |
|---|---|---|---|---|
| **Buzz** (Block, Apache 2.0) | Jul 2026 | Human–agent parity as cryptography — signed Nostr events, agents hold scoped keypairs tied to an owner, revocable individually | Agent identity as a credential, not `kind: 'agent'`. Chat merged with the forge: a git branch *is* a thread | Parity governs who may speak and sign. It says nothing about whether what was said was right. No claims, no status, no evidence |
| **Paperclip** (MIT) | Mar 2026 | Org chart as runtime — roles, budgets, approvals, heartbeat wakes, goal ancestry. Aimed at "zero-human companies" | Budgets as core primitives. Heartbeat wake as default. ~70k stars says the org metaphor lands | An orchestrator, not a place. No ambient conversation. Its goal — removing the human — is the opposite of yours |
| **Multica** (OSS) | 2026 | Agents as teammates you assign issues to; 23 agent CLIs; bridges into Slack/Lark/Telegram | Harness plurality shipped. Humility of bridging rather than replacing | A dashboard bolted onto someone else's chat; conversation and work record drift apart |
| **Mattermost / Zulip** | mature | Self-hosted chat that actually works | Zulip's topic model is the best threading design in the category | No agent model — but they set the floor on pure chat quality, and it is high |

**The gap.** Buzz proves *who* said it. Paperclip proves *who authorised* it. Multica
proves *what got done*. None keeps a record of what the organisation currently believes,
how confident it is, and what would change its mind. That is the ledger — an unoccupied
position, which is why C1 is the most serious finding here.

**The other gap.** None of the three is *nice to be in*. "At least a sleek, user-friendly,
beautiful communication app" is not a consolation prize; it is a differentiator none of
them is contesting.

## The risk you named, priced

Riskiest assumption #1 in the vision doc — "that debate improves output enough to justify
its cost" — was the right call, and the 2025–26 literature has moved against it:

- Most multi-agent-debate frameworks do not beat plain chain-of-thought at matched budget.
- Debate typically costs 3–10× a single well-designed agent.
- Homogeneous debate shows stance homogenisation and factual attrition.
- Isolated self-correction often beats unguided debate outright.
- Multi-agent wins in a narrow band: parallelisable, read-heavy work over independent sub-questions.

What survives is the good part: those are failures of *unguided, homogeneous* debate.
The design already avoids both — evidence outranks assertion, experiments break ties,
roles are assigned across model families. Heterogeneous debate with evidence weighting is
the configuration that still shows gains. But the value is in **measurement settling
arguments** and **the record of what was measured**. Position on the ledger, not the debate,
and keep the debate engine as small as it can be while still producing claim transitions.

**Week-one experiment.** One real architecture decision, three ways at matched token
budget: single strong model; same model self-critiquing; structured debate across three
families. Score blind. Record all three as claims in the ledger. If debate loses, the
product has falsified its own premise — the most convincing demo it could give, for ~$40.

## Build plan

Each phase has an exit gate. If the gate does not pass, the phase is not done.

**P0 — Make it run for a stranger (~1 day).** Portable `.env`, `.env.example`, one setup
script, `ignoreBuildErrors` off and 40 → 0, CI on typecheck and lint.
*Gate: fresh clone → one command → working app on a machine that has never seen the repo.*

**P1 — Falsify the premise before building on it (~3 days).** The matched-budget experiment
above. Deliberately before the redesign: if debate loses badly, the product is "a beautiful
agent-native chat app with an audit ledger" — still good, different roadmap.
*Gate: a written result with numbers and cost, either way.*

**P2 — Fix the ledger so it is a state machine (~1 week).** Stable claim identity;
`ClaimStatusChanged` carrying prior status, new status, triggering evidence, reason; debate
reads and appends. Ledger renders the transition trail.
*Gate: one claim, four status changes, one row, full trail. Replaying the log from seq 0
reproduces current state exactly. Duplicate claims impossible.*

**P3 — Rebuild the shell on real routes (~2 weeks).** Routes and deep links; one
discriminated conversation model resolved server-side; dense virtualised message list;
typed composer as the primary composer; keyboard navigation; both themes designed.
*Gate: every surface has a pasteable URL. 60 fps at 5,000 messages. Full keyboard
operation. No developer copy visible to users.*

**P4 — One honest agent in one channel (~1 week).** Not six simulated ones. One real agent
on a real harness, attention router actually gating wakes, visible budget, able to attach
evidence and move a claim.
*Gate: tier-1 deterministic rules cause ≥70% of useful wakes. Cost per resolved decision recorded.*

**P5 — Then the org layer.** Teams, gates as ledger queries, HR metrics, promotion.
Straightforward after P2, impossible before — as the vision doc already says.
*Gate: a gate that blocks a release from a ledger query, with a human able to read why in one screen.*

## Open questions

1. **Rebuild the shell, or renovate it?** — *Recommend:* keep `prisma/`, `src/lib/`, `docs/`;
   rebuild `src/app/` and `src/components/` on real routes.
2. **Who is the first user — you alone, or a team?** — *Recommend:* solo-first. One human,
   one assistant, one channel, ledger visible from day one.
3. **How different from Buzz do you want to look?** — *Recommend:* the graphite direction
   in the artifact. I would not ship the current palette.
4. **Local-first, or server-first with local as a mode?** — *Recommend:* single-process local
   now, every write through the event spine with a monotonic sequence, which keeps sync possible later.
5. **Desktop app, or browser?** — *Recommend:* build desktop-ready, wrap in Tauri at P3.
6. **What demo do you want to be able to give in six weeks?** — *Recommend:* the falsification
   demo with a real benchmark against a real storage engine.
7. **Which harnesses and models do I have?** — Model plurality is load-bearing; adversarial
   review needs the reviewer on a different family from the proposer.
